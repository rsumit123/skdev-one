Everything was learned from random initialization: the tokenizer, the language model and the chat behaviour. The code is nanochat (Andrej Karpathy's minimal LLM training stack); the work here is choosing the configuration, running it reliably on rented hardware, evaluating it fairly and shipping it.

The pipeline (click a stage)

1 · Tokenizer

A model reads integers, not text. The tokenizer maps text to a sequence of token ids drawn from a fixed vocabulary. We trained our own BPE (byte-pair encoding) tokenizer with a vocabulary of 32,768 on ~2B characters of the pretraining data.

How BPE works. Start from raw bytes. Repeatedly find the most frequent adjacent pair and merge it into a new token. Common words end up as one token ( sunlight); rare words are split into pieces (K|erala). Leading spaces are part of tokens, which is why most tokens below start with a space.

These splits come from the actual trained tokenizer. A typical English token is about 4–5 characters, which is why "bits per byte" (below) is used to compare models with different tokenizers.

2 · Architecture

A decoder-only Transformer, the same family as GPT-2/Llama, with modern refinements. The single knob is depth = 20; nanochat derives everything else from it: width = 20 × 64 = 1280, 10 attention heads of 128 dimensions, context of 2,048 tokens.

Attention lets each token look back at earlier tokens and pull in information. The MLP then processes each token on its own; it holds much of the model's "knowledge".

Residual connections mean each block adds a correction instead of replacing its input, so very deep stacks still train stably.

Model-level extras nanochat adds around the stack:

  • Smear: mixes a gated bit of the previous token's embedding into each token (cheap bigram signal).
  • x0 / residual lambdas: learned per-layer scalars that blend the original embedding back in.
  • Backout: subtracts a fraction of the layer-10 activations before the output, removing low-level features.
  • Logit soft-cap: output scores pass through 15·tanh(x/15), which prevents extreme values and stabilizes training.

Where the 897M parameters live

Why two numbers (897M vs 393M)? Embedding tables are lookups: a token id selects one row, so they cost memory but almost no compute. The 393M transformer weights do the multiplications on every token, which is the fairer number when comparing compute and capability (GPT-2's counts include its much smaller embeddings).

Sliding-window vs full attention

Each square is "token row may look at token column". Causal models only look backwards (lower triangle). A sliding window limits how far back. Here 32 squares stand for 2,048 tokens; the window is a quarter.

Why mix them? Sliding windows make 15 of 20 layers cheaper (attention cost grows with the square of what each token sees), while the 5 full layers still carry long-range information across the whole 2,048-token context.

3 · Pretraining

The model reads web text and learns one thing: predict the next token. Doing this well across billions of tokens forces it to learn grammar, facts and some reasoning.

Data: 3.48B tokens of ClimbMix

NVIDIA's ClimbMix is web text clustered by topic and re-weighted toward higher-quality clusters. Using it instead of plain FineWeb was one of the biggest wins in nanochat's speedrun history.

Data:param ratio 8 means ~8 training tokens per parameter of the scaling count. Chinchilla-style "compute-optimal" training uses ~10–20; 8 trades a little quality for a shorter run.

Optimizer: Muon + AdamW

Muon updates the big weight matrices. It orthogonalizes each update so every direction of the matrix learns at a similar rate, which trains faster than AdamW at this scale.

AdamW handles the embeddings, output layer and small scalars, where Muon does not apply.

FP8

Matrix multiplies in 121 of 132 linear layers ran in 8-bit floating point (H100 tensor cores do this at about 2× the bf16 rate). Master weights stay in fp32, so precision loss in the optimizer is avoided.

Run engineering

One script ran every stage on a rented H100. Checkpoints (model + optimizer state) were uploaded to a private Hugging Face repo every 500 steps so training could resume after a host failure, and the instance shuts itself down at the end or at a hard time limit.

4 · Chat fine-tuning (SFT)

A pretrained model only continues text. Supervised fine-tuning teaches it the shape of a conversation: whose turn it is, when to stop, how an assistant answers.

5 · Reinforcement learning on math

SFT copies answers from examples. Reinforcement learning instead lets the model try, scores the result, and pushes up whatever worked. Here the task is GSM8K grade-school math, where correctness is easy to check automatically.

Take 16 math problems
↓
Sample 16 answers to each (temperature 1.0)
↓
Reward = 1 if the final number is correct, else 0
↓
Advantage = reward − average reward for that problem
(better-than-average answers get reinforced, worse ones suppressed)
↓
Gradient step on the log-probabilities of the sampled tokens, weighted by advantage

nanochat calls this "GRPO", but it simplifies to REINFORCE with a group-mean baseline: no reference model or KL penalty, no PPO clipping, token-level normalization.

7 · Architecture experiment: MHA vs GQA vs MLA

The biggest serving cost today is the KV cache: every token of every conversation stores keys and values in every layer. It limits how many users fit on one GPU and how long contexts can be. I implemented multi-head latent attention (MLA), DeepSeek-V2's design, in nanochat (which does not ship it) and compared it with standard multi-head attention (MHA) and grouped-query attention (GQA) under an identical recipe.

Depth 12 (768 wide, 6 heads), 0.52B tokens each, same data, seed, optimizer and schedule; value embeddings off in all three. KV sizes for one 2,048-token sequence in bf16. Decode on one H100 with a 1,024-token prompt.

1 · A 3× smaller cache costs ~0.5–0.7% loss. GQA and MLA both fit 426 sequences in a 10 GB cache vs 142 for MHA, for a small quality hit. This is the trade-off production models make.
2 · At equal memory, MLA did not beat GQA here. The gap (0.002 bits/byte) is within single-seed noise. DeepSeek reports MLA ahead at much larger scale; no MLA-specific hyperparameters were tuned.
3 · MLA decoded ~2× slower. nanochat normalizes full keys (QK-norm), which blocks MLA's weight-absorption trick, so the cached latents are re-expanded into keys and values at every step.
Limits. One seed per variant, small model, short run. CORE at this size is noisy, so validation bits/byte is the main metric.

8 · Inference & serving

Generating text is a loop: run the model, pick the next token, append it, repeat. The KV cache stores each token's attention keys and values, so every new token only needs one new row of computation instead of re-reading the whole sequence.

One app.py serves a Gradio chat UI and an OpenAI-compatible API (/v1/chat/completions with streaming). A small control plane launches the GPU on demand, relays requests through a fixed HTTPS address, and destroys the instance after 45 idle minutes.

Tried and rejected: int8 quantization. On CPU it was slower (13.7 vs 16.2 tok/s) and lost ~6 points on ARC-Easy (48.0% vs 54.2%), so the demo stays in fp32.
